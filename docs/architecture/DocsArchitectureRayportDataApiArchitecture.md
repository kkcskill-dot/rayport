# 레이포트 데이터·API 아키텍처 제안

작성일: 2026-11-08. 상태: 설계안. 실DB 연결·서비스 기동·APIC 코드 검증·성능 측정은 수행하지 않았다.

## 1. 설계의 출발점

레이포트는 **이미 있는 업무 SQL과 반복 질문을, 권한·업무 정의·최신성·원천 부하 한도가 붙은 재사용 가능한 데이터 서비스로 전환하는 서버 설치형 제품**으로 제안한다. 핵심 산출물은 SQL 문자열이 아니라 승인된 `업무 기능`, 버전이 있는 `실행 계약`, 그 계약을 충족하는 `제공 경로`다.

2026-11-07 공통 기억에는 사용자가 Spharos Gateway보다 **APIC를 연결하고 싶다**고 결정한 기록이 있다. 이를 이어 **Rayport의 Oracle 직접 연결은 기본 구조에서 제외하고, 원천 실행은 APIC를 통과**하도록 권장한다. APIC를 외부 에이전트의 MCP 진입점으로 두는 것도 같은 방향의 설계 제안이다. Rust는 Rayport의 정책·의미 정의·요청·라우팅·마트 관리 계층, React는 사용자·DBA·운영자 화면을 담당한다.

이전 인계에는 APIC의 사람 신원 부재, 제한적인 MCP 스키마, SQL 첫 키워드 검사, 읽기 전용 트랜잭션 부재, 전역 타임아웃·속도 제한이 기록되어 있다. **현재 APIC 코드를 확인하지 않았으므로 현행 기능으로 단정하지 않는다.** 아래 통합 계약을 만족하는지 다시 검증하고, 만족하지 않으면 실데이터 POC 배포를 막는다.

기존 DW/DM은 정합성·장기 이력·공식 지표의 중요한 원천으로 재사용한다. 레이포트가 만드는 소규모 제공용 마트는 특정 기능의 빈도와 부하를 근거로 운영한다. 전체 기업 데이터웨어하우스를 새로 만드는 범위로 확대하지 않는다. 기존 MSTR 대체도 보고서군별 정의·권한·마감·배포 기능을 통과한 범위에서 판단한다.

## 2. 배치 구조와 책임 경계

```text
사람 → 기존 AX 포털 또는 React 업무 화면 → Rayport Rust API
기존 포털 에이전트 / 외부 에이전트 → APIC MCP 진입점 → Rayport 기능 API
                                  │
                 인증·권한 / 의미 계약 / 실행 경로 결정
                                  │
              ┌───────────────────┼───────────────────┐
              │                   │                   │
         승인 결과 캐시       제공용 마트         APIC 원천 API
                              PostgreSQL              │
                                              기존 DW·DM / 읽기 복제본
                                              승인된 제한 조회만 운영 원본

DBA 파일 반입 → 관측자료 저장 → SQL 후보 분석 → 기능/API 초안
정기 수집(선택) → APIC DBA 전용 프로젝트 → 같은 관측자료 저장
```

외부 에이전트용 APIC 경로와 원천 실행용 APIC 경로는 프로젝트·서비스 계정·라우트·허용 호출을 나눈다. APIC가 Rayport를 호출하고 Rayport가 APIC를 호출하는 구조에서 재귀 호출이 생기지 않도록 실행 방향과 대상 API allowlist를 고정한다. Rayport의 업무 API가 임의 APIC API나 SQL을 전달받아 실행하는 중계 프록시가 되어서는 안 된다.

| 구성 | 담당 책임 | 담당하지 않는 일 |
|---|---|---|
| React | 질문, 결과 근거, 기능 카탈로그, 생성 요청, DBA 후보 검토, 운영 현황 | 최종 권한 판정, SQL·비밀키 보관 |
| Rayport Rust | 사용자 컨텍스트, 의미 계약, 정책 결정, 경로 선택, 부하 예산, 요청 상태, 감사 | 기본 구성에서 Oracle 직접 접속 |
| APIC 통합 계층 | 승인 API만 원천 실행, 사용자 컨텍스트 검증, 실행 제한·취소, 원천 인증정보 격리 | 모델의 임의 SQL을 무검증 실행 |
| 제공용 PostgreSQL | 초기 영업일×점포 집계, 메타데이터·작업 상태·범위 원장 | 운영 Oracle의 범용 복제 또는 모든 이력 적재 |
| 파일 저장 | 반입 자료, 승인 이력 첨부, 내보내기, 마트 빌드 산출물 | 공개 디렉터리에서 원문 제공 |
| LLM 연결기 | 업무명·설명·질문 해석·후보 초안 보조 | 권한 결정, 실제 수치 생성, 승인 대행 |

초기는 Rust 모듈형 단일 서비스와 별도 작업 실행 프로세스로 시작한다. 같은 코드베이스에서 `api`와 `worker` 역할을 나누되 설치 시 단일 노드도 허용한다. 첫 버전에 Kafka·별도 벡터 DB·범용 분산 쿼리 엔진을 필수 구성으로 넣지 않는다. 이 구성과 PostgreSQL 선정은 설계 제안이며 설치나 기동이 완료된 상태가 아니다.

### 기존 AX 포털과 MCP 위치

기존 AX 포털·에이전트 연계를 우선하고 새로운 현업 포털 도입을 필수 조건으로 만들지 않는다. React 앱은 독립 설치 시 업무 화면과 공통 DBA·운영 콘솔을 제공한다. 기존 포털에 이미 대화·표·차트가 있으면 Rayport는 기능 목록·실행 결과·생성 요청 API를 제공하고, 필요 화면만 연결한다. AX의 모델 위치·인증 흐름은 아직 확인되지 않았다.

| MCP 위치 | 장점 | 비용·조건 | 선택 기준 |
|---|---|---|---|
| APIC 내부 | 사용자의 APIC 선호와 일치, 기존 인증·도구 공개 경로 재사용 가능 | APIC의 사용자 신원·스키마·버전·호출 방향 검증 및 확장 필요 | **우선 권장**. E1~E4 충족 여부부터 확인 |
| 별도 Rayport MCP 어댑터 | Rayport 계약을 직접 도구로 표현, APIC의 기존 기능 변경을 줄일 수 있음 | 운영 프로세스·인증 경계가 늘고 도구 정의 중복 위험 | APIC 확장 비용·일정이 더 크고 사용자 방향과 합의될 때 대안 |

두 방식 모두 업무 계약 카탈로그를 정의의 정본으로 두고 OpenAPI·MCP 도구 스키마를 같은 버전에서 생성한다. 양쪽 화면에서 입력 조건과 설명을 따로 편집하지 않는다. 게시된 MCP 도구의 계약 hash와 API 실행기의 hash 불일치는 호출 차단 사유다. 어댑터 선택이 원천 실행의 APIC 경유 원칙을 없애지는 않는다.

## 3. 제공 경로: 계약 충족 여부를 먼저 판단

조회 경로는 단순한 캐시→마트→원본 자동 폴백 체인이 아니다. **동일 업무 의미·허용 데이터 시점·행 권한·계약 버전을 충족하는 사전 승인 경로만** 후보가 된다. 후보 중 원천 영향이 작고 응답 SLA를 만족하는 경로를 선택한다.

| 경로 | 적합한 업무 | 반드시 확인할 조건 |
|---|---|---|
| 권한별 결과 캐시 | 동일 조건이 반복되는 조회 | 계약·권한 버전, TTL, 데이터 기준 시각, 원본 결과의 완전성 |
| 기존 DW/DM | 마감 실적, 장기 추이, 이미 정의된 공식 지표 | 영업일·마감 기준·갱신 지연·조직 이력·권한 호환 |
| 레이포트 제공용 마트 | 반복되는 점포×일 집계, 대시보드의 공통 조회 | 적재 비용을 포함한 순효과, 원천과의 검증, 오너, 갱신·폐기 정책 |
| 읽기 복제본 | 최신 데이터가 필요한 제한된 상세 조회 | 복제 지연, 조회 격리, 라이선스·환경 지원, 원본과의 의미 일치 |
| 운영 원본 | 대체 경로가 없는 소량·선택적 조회 | API별 명시 허용, 실행 예산, 최소 권한, 실취소, 업무 시간대 제한 |

운영 원본 경로는 기본 비활성이다. 캐시 미스·마트 장애·복제 지연이 발생해도 자동으로 운영 원본을 조회하지 않는다. 허용 가능한 오래된 자료가 있으면 기준 시각과 함께 제시하고, 없으면 대기·비동기 조회·새로운 제공 경로 요청 중 계약에 맞는 상태를 반환한다. 읽기 복제본도 원본의 redo 전송·apply·스토리지 자원을 쓸 수 있으므로 무부하 경로로 표현하지 않는다.

라우팅 의사코드:

```text
principal := verify_identity(request)
contract := load_published_contract(feature_id, version)
scope := authorize_per_contract(principal, requested_scope, contract)
reserve_disclosure_budget(principal, scope, contract)
candidates := routes_matching(contract.semantic_version, scope, freshness)
candidates := healthy_and_budget_available(candidates)
if candidates.empty: return explain_unavailable_or_async()
route := minimum_source_impact(candidates)
lease := atomically_reserve_route_budget(route, principal, scope)
if lease.denied: release_disclosure_reservation(); return explain_budget_limit()
try: run_fixed_plan(route, bound_parameters, scope, lease)
finally: settle_budget_only_after_execution_termination_confirmed(lease)
validate_result_envelope_and_commit_disclosure_ledger()
```

`healthy_and_budget_available`는 후보 선택용 힌트일 뿐 실행 권한을 보장하지 않는다. 최종 경로의 원천/마트 실행 예산은 실행 직전 원자적으로 예약한다. 취소·종료 미확인 작업의 lease는 계속 점유하고 별도 조정한다.

`reserve_disclosure_budget`는 동시 요청을 포함해 원자적으로 처리한다. 실행 실패·결과 미노출일 때는 예약을 해제하되, 이미 전달된 페이지 범위는 소비한 범위로 남긴다. 권한이 없는 조회를 새로운 기능 요청으로 바꾸어 우회시키지 않는다.

## 4. 운영 DB 부하를 줄이는 실질적 장치

### 4.1 원천 전체의 공동 예산

Rayport 대화, 대시보드, 다운로드, 마트 갱신, DBA 자료 수집이 **같은 원천 예산**을 공유한다. 사용자 화면 조회만 제한하고 백그라운드 작업은 무제한으로 실행하면 보호가 성립하지 않는다.

예산은 `source_id × workload_class × time_window`로 정의한다. 클래스는 대화 조회·예약 보고서·마트 갱신·관측자료 수집으로 나누며, 클래스 한도가 전체 한도를 초과하지 못한다. 노드 수가 늘어도 총량이 늘지 않도록 중앙 lease/예약을 사용한다. 정책 저장소 장애 시 신규 원천 조회는 차단한다.

필수 제한값:

- 원천별 동시 실행 수·연결 수, 사용자·기능별 요청률과 대기열 길이.
- 허용 조회 기간·점포/조직 범위·출력 행 수·반환 바이트·페이지 수.
- 실제 실행 전체 시간과 DB 호출 시간; 재시도 횟수와 총 예산.
- SQL별 논리 읽기·물리 읽기·CPU의 관측 상한 및 DB 측 보호 설정.
- 마트 최초 구축·정기 갱신·백필·스키마 수집의 실행 시간대와 1회 처리 범위.
- DB 건강 지표 및 데이터 수집 지연의 중단 기준. 지표 수집 자체의 비용도 한도에 포함.

구체 숫자는 DBA가 실제 원천 기준선과 업무 피크를 확인해 정한다. 개발 예시의 `3초`, `동시 2건` 같은 숫자를 고객 환경의 안전 보장으로 사용하지 않는다. QPS만으로 원천 부하를 대표하지 않으며, optimizer cost를 밀리초로 해석하지 않는다.

질문 단위 호출 예산 외에 사번×원천의 누적 실행 시간·조회 범위·재시도 예산을 유지한다. 새 대화·요청 ID·하루 단위 분할로 6개월 대량 조회 제한을 우회할 수 없게 한다. 이 실행 비용 원장은 공개 데이터 범위를 추적하는 권한 원장과 구분해 관리한다. DBA가 별도로 계획·승인한 최초 적재는 전용 배치 예산으로 처리하고, 일반 에이전트 호출 예산을 임의로 확장하지 않는다.

### 4.2 실행을 시작하기 전과 시작한 후

시작 전에는 고정 템플릿·타입 바인딩, 허용 기간, 선택도 조건, 금지 구문과 함수, 권한 필터, 승인된 실행계획 근거를 확인한다. `LIMIT` 또는 반환 행 수 제한은 대량 스캔을 막는 보장이 아니다. 원본에서 무작정 `EXPLAIN ANALYZE`나 시험 실행을 하지 않는다. 계획 수집도 가능한 기존 자료·검증 환경을 먼저 사용한다.

시작 후에는 실제 취소 API, DB 소비자 그룹 등 DB 측 제한, 연결 격리를 함께 적용한다. Oracle Resource Manager는 시간·CPU·I/O 등에 따른 SQL 취소나 세션 제어 기능을 제공한다. 어떤 기능을 적용할 수 있는지는 대상 버전·에디션·DBA 정책에 따라 검증한다. [Oracle Resource Manager](https://docs.oracle.com/en/database/oracle/oracle-database/19/admin/managing-resources-with-oracle-database-resource-manager.html)

APIC HTTP 요청이 시간 초과되었다는 이유로 원천 SQL까지 종료되었다고 판정하지 않는다. 실행 ID에 대한 취소와 종료 확인이 필요하다. 종료 상태를 확인하지 못하면 해당 연결·실행 예산을 즉시 재사용하지 않고 격리한다. 동일 쿼리 재시도에 따른 중복 부하를 막기 위해 실행 idempotency key와 처리 상태 조회가 필요하다.

### 4.3 보호 상태와 결과 표시

`정상 → 제한 → 신규 실행 대기 → 회복 확인 → 정상`을 별도 운영 상태로 둔다. 누적 위반이 있으면 기능별 자동 중지와 DBA 알림을 제공한다. 캐시나 마트는 정상이어도 원본만 제한된 상태를 구분한다.

답변에는 최소한 `데이터 기준 시각`, `적용한 기간·점포`, `업무 정의`, `제공 경로`, `완전성`을 붙인다. 사용자에게 내부 세션 ID·optimizer cost 같은 구현 정보를 상시 노출하지 않는다. DBA 상세 화면에서만 비용과 실행 근거를 보여준다.

## 5. ASH/AWR은 업무 API 발굴의 근거

### 5.1 수집 방식

기본 경로는 **BeLoga 형식과 호환 가능한 파일의 오프라인 반입**이다. 현재 Mac에서 BeLoga 파일 스키마를 검증하지 않았으므로 호환성을 완료 상태로 표시하지 않는다. 반입 어댑터에서 실제 파일 스키마를 확인하고 버전 매핑을 고정해야 한다. 업로드한 HTML 보고서의 스크립트는 실행하지 않고, 텍스트와 표만 정규화한다.

반입 묶음에는 자료 종류, DB 식별 범위, 인스턴스/PDB, DB 버전, 시간대, 관측 시작·종료, 누락 구간, 추출 방식, 수집 조건, 파일 checksum을 포함한다. SQL 원문, 통계, 계획 객체, bind 메타데이터, 컬럼·테이블 설명, 업무 모듈 힌트를 서로 다른 데이터셋으로 저장한다. 반입 자료가 잘렸거나 SQL 원문이 일부만 있으면 후보에 그 한계를 보존한다.

정기 수집이 필요할 때만 APIC의 DBA 전용 프로젝트에 승인된 자료 추출 API를 등록한다. 상한 있는 시간 구간과 증분 cursor를 사용하고 SQL 원문은 미수집 fingerprint만 가져온다. 백필·동시 수집·수집 주기를 제한한다. 원천 DBA 권한을 일반 대화 기능에 넘기지 않는다.

### 5.2 ASH와 AWR을 혼동하지 않는 데이터 모델

Oracle 문서상 ASH는 활성 세션을 1초 단위로 표본화한다. 따라서 오래 실행되거나 기다리는 SQL이 더 많이 관측될 수 있고, 짧고 빈번한 업무 SQL은 누락될 수 있다. **ASH 표본 수를 실행 횟수·사용자 수·업무 거래 수로 표시하지 않는다.** 디스크에 보존되는 표본도 전체 메모리 표본과 같지 않을 수 있다. [ASH 정의](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/V-ACTIVE_SESSION_HISTORY.html), [ASH 보존 특성](https://docs.oracle.com/en/database/oracle/oracle-database/19/tgdba/measuring-database-performance.html)

`DBA_HIST_SQLSTAT`은 기준에 따라 상위 SQL 통계를 포착한다. 실행 횟수는 관측 구간의 `EXECUTIONS_DELTA` 등 통계에서 가져오고, 전사 전체 실행 횟수로 확대 해석하지 않는다. `DBA_HIST_SQLTEXT`도 저장소에 포착된 SQL의 텍스트를 제공한다. 자료에 없는 SQL은 `0회` 대신 `관측 근거 없음`이다. [SQLSTAT](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/DBA_HIST_SQLSTAT.html), [SQLTEXT](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/DBA_HIST_SQLTEXT.html)

동일 SQL을 합칠 때 DBID·PDB·인스턴스·스냅샷·계획을 보존한다. SQL_ID만 같은 다른 DB를 합치지 않는다. 재기동·스냅샷 누락·계획 변경·중복 반입을 분리한다. 병렬 SQL의 DB 자원 시간과 API 호출의 벽시계 응답 시간을 구분하고, 관측 누락이 있는 구간을 추정치로 자동 메우지 않는다.

화면에는 다음 세 항목을 별도 표시한다.

| 항목 | 의미 | 사용 목적 |
|---|---|---|
| 관측 실행 수 | AWR 또는 애플리케이션 계측에서 확인한 실행 통계 | 재사용 수요의 한 근거 |
| 활성 표본·대기 분포 | ASH에서 관측한 세션 활동 | 운영 영향·병목·시간대 분석 |
| 질문·기능 호출 수 | Rayport에서 실제 요청한 수 | 신규 수요 및 마트 후보 선정 |

바인드 캡처에는 값이 없거나 일부만 있을 수 있으며, 일부 타입·위치 제약도 있다. 값 하나를 API의 기본값이나 허용값 전체로 확정하지 않는다. 실제 bind 값은 개인정보일 수 있으므로 기본 반입 대상은 타입·위치·길이 등 메타데이터다. [Oracle bind capture](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/V-SQL_BIND_CAPTURE.html)

### 5.3 사용권과 기능 활성화

Oracle 19c 문서에서 ASH와 대부분의 AWR 자료 접근은 Diagnostics Pack 범위에 해당하며, 일부 `DBA_HIST_*` 뷰에는 예외가 있다. **직접 SQL 조회나 파일 반입을 사용권 우회 수단으로 안내하지 않는다.** 대상 버전·에디션·계약의 사용권 확인을 연결 프로필에 남기고, 확인 전에는 해당 수집 어댑터를 비활성으로 둔다. `CONTROL_MANAGEMENT_PACK_ACCESS` 설정값만으로 라이선스 보유를 판정하지 않는다. 미보유 환경은 애플리케이션 계측·사용자가 승인한 SQL 등록·이미 적법하게 제공된 메타데이터 경로로 시작한다. Active Data Guard의 실시간 조회 기능도 별도 적용 조건이 있으므로 단순히 복제본을 무료 대안으로 제시하지 않는다. [Oracle 라이선스 문서](https://docs.oracle.com/en/database/oracle/oracle-database/19/dblic/Licensing-Information.html)

### 5.4 분석 단계와 후보 분류

1. **정규화:** Oracle 문법을 이해하는 parser로 읽기 구문·의존 객체·바인드·주석의 모듈 힌트를 추출한다. SQL 첫 단어만 검사하지 않는다. parser가 이해하지 못한 구문은 미지원으로 남긴다.
2. **군집화:** literal을 제거한 구조 fingerprint, 조인·필터·집계 grain, 모듈·업무 태그를 함께 사용한다. 상수의 차이가 업무 의미를 바꾸는 경우 자동 병합하지 않는다.
3. **업무 해석:** 테이블·컬럼 설명, 보고서 정의, SQL 주석, 담당자의 설명을 근거로 업무명을 제안한다. 확정 정의와 추정을 구분한다.
4. **경로 제안:** 소량 상세 조회는 고정 API, 반복 집계는 제공용 마트, 이미 있는 DW/DM과 일치하면 기존 지표 연결을 제안한다. 무겁고 드문 조회는 비동기·예약 실행을 우선한다.
5. **후보 우선순위:** 반복 수요, 관측 자원 비용, 재사용 가능한 조건, 최신성 요구, 정책 제약, 증거 완전성을 각각 보여준다. 단일 AI 점수만으로 자동 배포하지 않는다.

DBA 화면의 요약 예시: `점포별 일매출 조회가 반복 관측되었습니다. 현재 SQL은 집계 비용이 큽니다. 기존 마감 DM과 정의를 비교한 뒤, 일×점포 마트로 제공하는 방안을 제안합니다.` 이는 실제 분석 결과가 아니라 화면 문구 예시다.

## 6. 자동 API는 초안 생성부터 자동화

상태 전이는 `발굴 → 의미 확인 → 계약 초안 → 검증 → 승인 대기 → 게시 → 관찰 → 중지/폐기`로 한다. 중간 상태는 API 소비자에게 공개하지 않는다. 게시된 버전 수정은 새 버전과 새 검증 기록으로 처리한다.

자동 생성 범위는 다음과 같다.

- 기능명·설명·예시 질문과 출처 SQL 연결.
- 고정 SQL/조회 계획, 입력·출력 JSON Schema, OpenAPI, API 예시.
- 필수 기간과 점포 조건, 정렬 allowlist, 행·바이트 상한.
- 업무 정의·grain·통화·시간대·마감 기준·갱신 허용 지연의 초안.
- 필요한 권한, 민감 필드, RLS 정책, 제공 경로, 캐시 키 구성의 초안.
- 검증 케이스와 오너 검토 항목, APIC 게시용 선언형 아티팩트.

모델이 Rust 소스 코드를 운영 서버에서 컴파일해 실행하는 구조는 사용하지 않는다. 초기에는 **검증된 선언형 계약을 고정 실행기로 실행**한다. API를 게시할 때마다 실행기 코드를 새로 배포할 필요가 없게 한다. 이때 APIC가 지원하는 게시 방식과 스키마 표현 능력을 별도 확인해야 한다.

검증은 다음 항목을 통과해야 한다.

| 검증 | 통과 조건 |
|---|---|
| 업무 의미 | 업무 오너가 매출·반품·취소·마감·영업일·조직 이력 정의를 확인 |
| SQL 의미 | 원래 조회와 생성 계약이 같은 집계 단위·필터·NULL·중복·기간 경계를 가짐 |
| 읽기 안전성 | DML/DDL/PLSQL·`FOR UPDATE`·위험 함수·DB link 등 미승인 기능 차단; 읽기 권한도 최소화 |
| 매개변수 | 실제 바인딩 사용; 컬럼·테이블·정렬 식별자는 고정 allowlist; 자유 SQL 미수신 |
| 권한 | 사용자 신원·점포 범위가 서버에서 정해지고 APIC/원천 실행까지 강제됨 |
| 비용 | 검증 환경과 승인된 조건에서 측정, 실패·폭주·취소·지연 시나리오 통과 |
| 정합성 | 대표 정상·경계·취소·수정·지연 자료를 공식 보고서 또는 검증 SQL과 대조 |
| 공개 계약 | 버전·오너·SLA·최신성·문제 응답·변경 영향이 명시됨 |

단순 `SELECT`도 함수 호출이나 외부 경로를 통해 부작용을 만들 수 있다. 읽기 전용 계정/트랜잭션, 허용 객체·함수, SQL AST 검증을 함께 사용한다. 보안 필터를 사용자 SQL 문자열 뒤에 붙이는 방식 대신 검증된 고정 템플릿 또는 권한 뷰를 사용한다.

의미 동등성은 모든 SQL에 자동 증명할 수 없다. 애플리케이션이 여러 SQL 결과를 합치거나 특정 세션 컨텍스트·임시 테이블·패키지 상태에 의존하면 후보에 제약을 표시하고 수동 설계로 넘긴다. ASH/AWR만으로 화면의 전체 업무 흐름이나 트랜잭션 의미를 복원했다고 주장하지 않는다.

승인은 업무 오너의 정의 확인과 DBA의 실행 경로·예산 확인을 분리한다. 개인정보·권한 정책이 달라지는 기능은 정책 오너 확인도 포함한다. 이 절차는 실제 제품의 게시 정책 설계이며, 이 설계 문서 작성을 위해 사용자에게 별도 승인을 요구하는 의미는 아니다.

## 7. 자주 쓰는 조회를 사전 구성하는 마트

### 7.1 초기 마트의 범위

첫 단위는 이전 설계 기록에 맞춰 **영업일 × 점포**의 PostgreSQL 집계를 권장한다. 지표는 업무 정의가 확정된 것만 포함한다. 순매출·취소·반품의 기준이 미확정이므로 현재 문서에서는 계산식을 확정하지 않는다. 고객·상품·거래 상세 전체를 첫 단계에 복제하지 않는다.

판매·재고·정산·매입 등 업무별 사전 패키지는 **의미 정의·필수 필드·예시 질문·권한·검증 사례·갱신 정책**의 템플릿으로 제공한다. 고객사의 테이블명을 추정해 자동 적용하지 않는다. 설치 마법사에서 원천 매핑과 업무 정의 차이를 확인한 후 개별 기능을 활성화한다.

마트는 대형 테이블 하나가 아니라 다음과 같은 관리 객체다.

```text
MartDefinition {
  id, owner, business_definition_version,
  grain, dimensions, measures, source_contract_ids,
  security_dimensions, refresh_mode, allowed_lateness,
  refresh_budget, retention, quality_rules,
  refresh_watermark, published_snapshot_id, expires_at
}
```

점포 권한을 적용할 수 있는 차원을 집계에서 제거하지 않는다. 전체 점포를 합친 결과를 나중에 특정 점포 사용자에게 재사용할 수는 없다. 지표 정의·권한 정책이 바뀌면 관련 마트·캐시·다운로드를 무효화하거나 새 버전으로 갱신한다.

### 7.2 비용을 포함한 후보 선정

추천 기준은 `반복 호출 × 원천 조회 비용`과 `초기 구축 + 갱신 + 저장 + 운영 비용`의 비교다. 같은 시간 구간·같은 측정 단위로 비교하며 측정치와 추정치를 나눈다. “쿼리 수 90% 감소”를 “DB 부하 90% 감소”로 바꾸지 않는다.

반복되는 짧은 조회는 결과 캐시만으로 충분할 수 있다. 폭넓은 조건으로 반복되는 집계는 마트가 유리할 수 있다. 매우 최신이어야 하는 값, 변경이 잦아 전체 재집계가 필요한 값, 거의 쓰이지 않는 값은 마트 유지비가 더 클 수 있다. 초기에는 권고안과 비용 근거를 제공하고 자동 생성·확장·폐기는 운영 정책이 정해진 후 허용한다.

### 7.3 적재와 갱신의 정확성

가장 먼저 기존 DW/DM 또는 승인된 집계 API를 재사용한다. 증분 기준이 신뢰 가능할 때는 변경분을 가져오고, 그렇지 않으면 제한된 영업일 구간 재집계처럼 검증 가능한 방식을 택한다. `MAX(updated_at)`만 따라가는 방식은 삭제·과거 수정·같은 시각의 레코드·늦게 도착한 변경을 놓칠 수 있으므로 그대로 일반화하지 않는다.

갱신은 `원천 기준점 확보 → 제한 범위 추출 → staging → 품질 검증 → 원자적 게시 → watermark 갱신`으로 처리한다. 이전 완성본과 생성 중인 버전이 섞이지 않게 한다. 실패하면 watermark를 진전시키지 않고, 같은 작업 ID 재실행은 멱등이어야 한다. 확정 실적은 단일 snapshot 또는 불변 마감 자료를 요구한다. 원천에서 범위 일관성을 제공하지 못하면 합계 대사 통과만으로 이를 보장할 수 없으며, 명시 승인된 잠정 자료 계약으로만 공개한다. 변경되지 않은 partition도 새 데이터셋 버전에 포함하는 규칙은 대표 마트 설계를 따른다.

CDC는 필요할 때 선택하는 별도 통합 단계다. 초기 snapshot의 부하, 로그 보존·supplemental logging, 삭제·PK 변경·스키마 변경, 이벤트 중복·역순·트랜잭션 경계, 재시작 offset, gap 후 재동기화를 다룬다. CDC를 켠다는 이유만으로 원천 비용이 사라지지 않는다. Debezium Oracle 문서도 archive log와 supplemental logging 등의 준비 및 초기 snapshot을 설명하며, 추가 logging은 redo량에 영향을 줄 수 있다. [Debezium Oracle connector](https://debezium.io/documentation/reference/connectors/oracle.html)

집계 갱신에서는 반품·취소·과거 매출 수정으로 이전 영업일 버킷을 다시 계산해야 할 수 있다. 최근 N일 재처리와 장기 수정 이벤트의 표적 재계산을 구분한다. join 대상 차원 변경이 과거 실적을 재작성해야 하는지, 당시 조직 기준을 보존해야 하는지도 업무 계약에 포함한다.

### 7.4 마트 수명주기

`제안 → 매핑·정의 확인 → 시험 구축 → 검증 → 게시 → 사용·비용 관찰 → 갱신 조정 → 폐기 제안`으로 관리한다. 미사용 기간, 갱신 비용, 중복 마트, 소비 API 의존 관계를 보여준다. 폐기 전에 소비자 영향과 이력 보존을 확인한다. 스케줄러는 jitter·중복 방지 lease·최대 지연·실패 backoff를 지원한다.

## 8. 질문에 기능이 없을 때 생성 요청

질문 해석 결과는 다음을 구분한다.

- `사용 가능`: 승인된 기능과 조건이 맞아 실행할 수 있음.
- `추가 조건 필요`: 기간·점포·기준이 모호해 짧은 확인이 필요함.
- `권한 확인 필요`: 기능은 있으나 사용자가 허용되지 않음. 존재 정보 노출도 정책에 따름.
- `최신성/경로 부족`: 기능은 있으나 요청 시점을 제공할 수 없음.
- `기능 없음`: 적합한 승인 계약이 없어 생성 요청으로 전환 가능함.

`기능 없음`에서는 질문·원하는 출력·필요 주기·최신성·대상 점포를 채운 요청 초안을 바로 보여준다. **질문을 했다는 이유만으로 운영 API를 생성·게시하지 않는다.** 사용자가 `생성 요청`을 누르면 저장하고, 중복 요청이 있으면 합류 또는 기존 요청 보기로 안내한다. 요청 등록은 즉시 가능하게 하고 개발자가 다시 요구사항을 복사하게 하지 않는다.

요청은 `접수 → 중복/기존 기능 확인 → 자료·정의 보완 → 후보 설계 → 검증 → 승인 → 게시 → 원질문 다시 실행 가능` 상태를 갖는다. 기존 SQL 후보·마트·DW 지표를 역검색해 새 개발 전에 재사용을 우선한다. 담당자와 다음 작업이 없으면 진행 중으로 표현하지 않는다. 승인 전 결과를 모델이 수치로 만들어 답하지 않는다.

요청에는 목적·필요 항목·기존 기능의 부족한 범위만 전달하고 관련 없는 대화 전체를 첨부하지 않는다. 원질문에 `어제`가 있었다면 접수 시 해석한 절대 날짜와 원문을 함께 보관한다. 게시 후에는 `당시 날짜로 확인`과 `현재 기준으로 다시 실행`을 구분한다. 완료는 API 등록이 아니라 원래 질문의 조건을 충족하는 결과 또는 해결된 대안이 확인된 상태다.

### 분석과 결과 재사용의 경계

각 기능은 지원 지표·차원·필터·기간·비교·상세조회 범위를 선언한다. 표 정렬·차트 변경·허용된 재집계는 저장된 결과에서 처리하고, 새로운 기간이나 차원이 필요할 때만 추가 호출을 검토한다. 상품군이 없는 점포 매출로 상품군별 실적을 만들지 않는다.

합계·증감률·순위는 검증된 계산기에서 수행하고 LLM은 설명을 맡는다. 비율은 분자·분모로 다시 계산하며 일별 고유 고객 수를 합쳐 연간 고유 고객 수로 쓰지 않는다. 여러 API 결과의 결합은 grain·키·기간·통화·업무 정의가 확인된 경우로 제한한다. 마트와 최신분을 합칠 때도 확정된 기준점으로 범위를 나눠 중복·누락을 방지한다. 관측된 변화와 원인 가설은 답변에서 분리한다.

저장한 질문은 재실행 정의이고, 저장한 결과는 특정 시점의 스냅샷이다. 스냅샷 열람 시에도 현재 권한을 검사한다. 과거 원천 상태가 보존되지 않았다면 당시 상태를 새 조회로 복원할 수 있다고 안내하지 않는다.

## 10. APIC와의 필수 통합 계약

### E1. 사람 신원과 실행 주체

APIC의 프로젝트 API key는 서비스 인증이다. 사람의 사번·조직·점포 범위를 대신하지 않는다. Rayport가 검증한 주체를 audience·issuer·expiry·request ID가 있는 서명 컨텍스트로 전달하고, APIC에서 다시 검증한다. 브라우저가 임의로 설정한 `employee_id`나 `store_ids`를 신뢰하지 않는다. 토큰 발급자와 권한 정본은 아직 미확정이다.

### E2. 원천 실행에서의 권한 강제

APIC/원천에서 사용자 범위가 강제되거나, 공격자가 Rayport를 우회해 넓은 API를 호출할 수 없다는 동등한 구조가 검증되어야 한다. Rayport UI만 필터링하는 방식은 불충분하다. 캐시·마트·다운로드에서도 같은 정책 버전을 적용한다. 여러 날·점포를 나눠 조회하는 누적 공개 우회는 사번 기준 범위 원장으로 검증한다. 민감 집계는 작은 집단 추론·차분 조회에 대한 별도 정책이 필요한지 정한다.

### E3. 실행 안전성과 중단

고정 API ID, 엄격한 입력 스키마, 승인 SQL template hash, 최소 권한, 읽기 안전성, API별 timeout·최대 결과·동시성, 실행 ID와 취소·종료 확인이 필요하다. 전역 30초 timeout과 공통 rate limit만으로 업무별 원천 보호를 충족했다고 보지 않는다.

### E4. 결과·근거 계약

APIC 응답은 실제 적용 범위·데이터 기준점·source route·계약 버전·잘림 여부·실행 상태를 제공해야 한다. MCP가 배열·enum·형식·설명·범위를 충분히 표현하지 못하면 Rayport가 반환한 계약을 그대로 전달하거나 제한된 도구 wrapper를 설계한다. 최종 방식은 현재 APIC 코드 확인 후 정한다.

### 캐시·연결 풀 격리

캐시 키는 최소 `tenant/project + capability/version + semantic/policy version + 정규화 파라미터 + 유효 권한 범위 hash + snapshot/watermark`를 포함한다. 역할명만 같다는 이유로 결과를 공유하지 않는다. 사용자 고유 정책이 있으면 주체 ID 또는 충분히 검증된 정책 컨텍스트까지 포함한다. 권한 회수 시 캐시와 미완료 다운로드를 즉시 무효화할 수 있어야 한다.

연결 풀에서 사용자 컨텍스트·세션 변수·임시 객체가 다음 요청으로 새지 않도록 APIC에서 설정·정리·실패 시 폐기를 검증한다. 순수 서비스 계정 원천 접속이라도 사용자별 정책이 원천 SQL에 어떻게 반영되는지 감사 가능해야 한다.

## 11. Rust·React 구현과 설치 운영

### 모듈 경계 제안

Rust는 `identity`, `policy`, `catalog`, `semantic`, `planner`, `apic_client`, `evidence_import`, `candidate_mining`, `mart_jobs`, `requests`, `audit`의 책임 경계를 둔다. React는 서버 계약에서 타입을 생성하고 질문·결과·요청·후보 검토를 같은 기능 ID로 연결한다. UI에서 SQL을 직접 만들어 보내지 않는다.

Oracle 직접 연결을 기본에서 제외하는 이유에는 배포 제약도 있다. `oracle` Rust crate는 ODPI-C 기반이며 Oracle Client 런타임이 필요하다. 이 경로를 추후 선택하려면 지원 OS·아키텍처·Client·DB 버전과 배포 조건을 검증해야 한다. [rust-oracle](https://docs.rs/oracle/latest/oracle/), [ODPI-C 설치](https://oracle.github.io/odpi/doc/installation.html)

추후 직접 연결 연구에서도 HTTP timeout이나 Rust task 취소만으로 DB 실행을 끊었다고 가정해서는 안 된다. `spawn_blocking` 작업은 시작 후 일반 abort로 취소되지 않으며, rust-oracle의 call timeout은 전체 쿼리 시간이 아닌 개별 왕복에 적용된다. 별도 실행 취소와 종료 확인이 필요하다. 이는 APIC 실행 계약에서도 확인할 핵심 의미다. [Tokio 작업 취소](https://docs.rs/tokio/latest/tokio/task/), [rust-oracle Connection](https://docs.rs/oracle/latest/oracle/struct.Connection.html)

### 서버 설치 패키지

초기 지원 대상으로 Linux x86_64를 제안하되 실제 고객 OS 확인 전 확정하지 않는다. Rust 바이너리·React 정적 산출물·설정 예시·migration·운영 명령을 버전이 맞는 한 묶음으로 배포한다. 컨테이너와 systemd 중 고객 운영 표준에 맞는 설치 프로필을 제공한다. 빌드 가능한 상태와 배포 가능한 상태를 구분하며, 고객 서버에서 인터넷 패키지 설치를 전제로 하지 않는다.

망분리 환경에서는 사내 LLM endpoint를 기본으로 연결하고 외부 송신은 명시 설정한 대상만 허용한다. SQL 원문·bind·스키마·결과 중 어떤 항목을 LLM으로 보낼지 구분하고, 기본은 최소화한 스키마/설명/관측 요약이다. LLM이 없어도 등록 기능 실행·마트 갱신·수동 요청·파일 반입은 동작하도록 한다. 프롬프트와 모델 버전은 초안의 추적 정보이며 승인 근거 자체는 아니다.

TLS, SSO/OIDC, 비밀 참조와 교체, 감사 기록, 백업·복구, 데이터 보존·삭제 정책을 설치 점검에 포함한다. 원천 비밀번호는 브라우저에 전달하지 않는다. 파일 저장소의 개인·실제 고객 자료는 소스 저장소에서 제외한다.

### HA와 복구

확장 시 API는 무상태 다중 노드, 작업은 lease·fencing token으로 중복 실행을 차단한다. 노드별 semaphore만으로 전체 원천 한도를 관리하지 않는다. 원천 실행·마트 게시·감사 상태의 중복 처리와 재시작을 검증한다. PostgreSQL의 복구·스키마 migration·버전 롤백 계획과 마트 재생성 절차를 분리한다. 마트 갱신 실패가 기존 완성본을 삭제하지 않게 한다.

RPO/RTO와 보존 기간은 고객 요구에 따라 정한다. 배포 전 검증 항목에는 권한 저장소 장애, APIC timeout·부분 응답, 취소 실패, 원천 지연, worker 중복, 마트 손상·복구를 포함한다. 요청이 불명확하게 종료되면 원천 실행이 다시 중복 시작되지 않도록 실행 상태를 조정하는 절차가 필요하다.

POC의 핵심 검증은 보기 좋은 데모보다 **한 보고서군에서 같은 업무 답을 권한대로 제공하면서 원천의 순부하를 실제로 낮추는지**다. 비교 구간의 업무량·시간대·자료 범위를 맞추고, 원천 DB 시간/논리 읽기/물리 읽기, 사용자 지연, 마트 적재 비용, 최신성 위반, 권한 거부·누적 범위 차단을 함께 기록한다. 이 문서에는 측정되지 않은 절감률을 넣지 않았다.

아직 필요한 실제 환경 정보는 순매출·취소·마감 정의, 원천/분석계 구조, 점포 권한 정본, 토큰 발급자, APIC 현행 구현, Diagnostics Pack 사용권·보존 설정, POC 대상 보고서군, DBA 부하 기준이다. 이는 다음 구현 단계의 입력이며, 현재 설계 문서 작성 자체를 막는 조건은 아니다.
