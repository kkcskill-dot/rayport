# 레이포트 제품 설계 v0.3

작성일: 2026-11-08. 상태: 검토 가능한 설계안. 현재 코드의 구현 범위를 뜻하지 않는다.

## 1. 제품의 중심

**레이포트는 기존 업무 SQL을 안전하게 재사용할 수 있는 분석 도구로 전환하고, 현업 질문을 통해 필요한 API와 소규모 마트를 계속 확장하는 서버 설치형 플랫폼이다.**

현업에게는 “업무 데이터를 물어보는 곳”, DBA에게는 “업무 SQL을 발굴해 통제된 데이터 서비스로 만드는 곳”, 조직에는 “누가 무엇을 필요로 하는지와 어떤 데이터 자산으로 해결했는지 남기는 곳”이다.

제품의 최소 단위는 SQL이나 대시보드가 아니라 **업무 도구**다. 업무 도구 하나에 지표 의미·입력/출력·지원 차원·권한·신선도·부하 한도·담당자·버전·검증 질문이 함께 붙는다. 동일 계약을 UI, API, MCP가 공유한다.

## 2. 확정·근거·제안의 구분

| 구분 | 내용 |
|---|---|
| 이번 사용자 요구 | 서버 설치형, Rust + React, 유사 솔루션 비교와 UI/UX 설계, DW/DM 차별화, 잦은 조회의 사전 마트, 원천 부하 최소화, ASH/AWR에서 업무 쿼리 발굴과 API 자동 생성 제안, 없는 기능의 생성 요청 |
| 기존 사용자 결정 | APIC 연동 선호. 신규 제품명 Rayport. 현업 자연어 분석. 반복 실적 집계와 MSTR 보고서군별 대체 검토 |
| 확인한 로컬 자료 | 공통 기억 2026-11-07 인계, Downloads의 `apic_ai_analytics_agent_prompt.txt`. 현재 프로젝트 폴더는 시작 시 비어 있었음 |
| 확인하지 못함 | 다른 Mac의 DESIGN.md 원문, 최신 APIC 코드·설치 상태, 실제 DB/권한/사용권/보고서 정의 |
| 이번 권장안 | APIC 실행 경로 재사용, 초기 PostgreSQL 메타데이터·집계, 승인 후 API 공개, 사내 모델 연결 옵션, 매출 업무 POC |

과거 인계에 적힌 APIC 제약은 현행 코드의 결함 확정이 아니다. 실제 코드 재확인 전까지 설계상 검증 과제로 둔다. 원본 지시문의 기획 중심 범위를 유지하고 초기 구조와 UI 시연만 추가한다.

## 3. DW·DM과 어떻게 다른가

| 관점 | DW | 전통적 DM | 레이포트 권장 접근 |
|---|---|---|---|
| 시작점 | 통합 이력·공통 데이터 모델 | 부서·업무 주제별 분석 모델 | 기존 업무 SQL·승인 API·실제 질문 |
| 제공 단위 | 정제 데이터와 전사 지표 | 주제별 데이터셋·집계 | 업무 의미와 운영 계약이 붙은 API/MCP 도구 |
| 데이터 확보 | 장기 통합·품질·이력 관리 | 필요한 주제의 상세·집계 적재 | 기존 DW/DM 우선 재사용, 필요한 집계만 추가 |
| 신규 요구 | 모델·파이프라인·리포트 변경 | 데이터셋과 분석 모델 확장 | 질문에서 기존 도구 연결·확장·신규 요청까지 추적 |
| 운영 원천 보호 | 별도 저장소·적재 정책에 의존 | 적재·조회 설계에 의존 | 조회·수집·마트 갱신을 하나의 원천별 부하 예산으로 관리 |

이 표는 전형적인 역할 구분이며, 최신 DW/BI 플랫폼이 실시간 분석이나 AI를 제공하지 않는다는 뜻이 아니다. 레이포트 내부의 영속 집계는 **실제로 DM**이다. 제품은 DM을 숨기거나 부정하지 않고 생성·사용·갱신·폐기까지 관리한다.

기존 DW/DM이 없어도 승인된 업무 SQL과 APIC로 작게 시작할 수 있다. 기존 AX 포털 연동만으로 도입할 수 있으며 별도 현업 포털은 선택 사항이다.

레이포트가 전체 DW를 다시 만들면 초기 도입 비용과 운영 책임이 급증한다. 전사 이력 정합성, 모든 원천 통합, 규제 보관, 복잡한 전사 모델은 기존 DW의 책임으로 유지하고 필요한 조회를 연결한다. MSTR도 보고서·배포·권한·출력 품질을 하나씩 검증한 업무군만 대체한다.

## 4. 차별화 가설

1. **DBA의 기존 자산에서 출발**: ASH/AWR·업무 로그·승인 SQL을 업무별로 묶고 API 후보와 집계 후보를 함께 제시한다.
2. **원천 부하까지 포함한 업무 계약**: 질문 하나뿐 아니라 동일 사용자·원천의 누적 호출, 동시성, 실제 취소, 마트 유지 비용을 통제한다.
3. **질문에서 공급까지 연결**: 도구 부족을 요청으로 변환하고 담당자·검증·게시·원래 질문 재실행을 추적한다.
4. **설치된 환경을 활용**: APIC, 기존 AX 포털, DW/DM, 사내 인증과 모델을 연결해 도입 범위를 줄인다.

AI 대화, MCP, API 자동 생성, 자동 집계는 각각 기존 제품에도 있다. 이 네 가지를 Oracle 운영 환경과 APIC에 맞게 일관되게 제공하는 것이 차별화 가설이며, 독점성·성능·비용 우위는 아직 검증되지 않았다. 상세 출처는 02 문서에 있다.

## 5. 대표 사용자 여정

### 현업: 질문을 해결한다

1. “어제 우리 점포 매출이 전주보다 얼마나 줄었어?”를 입력한다.
2. 화면에 절대 날짜, 허용 점포, 순매출 정의, 비교 기간을 칩으로 표시한다. 영업일·취소 기준이 모호할 때만 추가 확인한다.
3. 권한과 기능 범위를 만족하는 도구를 찾고 캐시·마트·기존 DW·APIC 승인 조회 중 계약을 충족하는 경로를 고른다.
4. 검증된 계산기로 증감·순위를 계산하고 표·차트·데이터 기준 시각·범위를 함께 보여 준다.
5. “상품군별로도 보여줘”에 필요한 차원이 없으면 “현재 도구는 점포별 매출을 지원합니다. 상품군 분석을 요청할 수 있습니다.”와 요청 초안을 제시한다.
6. `생성 요청`을 누르면 원문·의도·필요 차원·희망 신선도·현재 부족한 기능을 저장한다. 관련 없는 대화 전체를 전달하지 않는다.
7. 승인·검증 후 도구가 공개되면 원래 대화에 `준비됨 · 다시 분석`이 나타난다. 요청 당시 날짜/현재 날짜 중 무엇인지 다시 선택한다.

예제 업무 숫자와 후보 점수는 시안에서 모두 가상이다. 실제 매출이나 성능 개선 실적으로 표현하지 않는다.

### DBA: 업무 API 후보를 검토한다

원자료 SQL 목록보다 “점포별 일매출 조회로 추정됩니다. 관련 SQL 4개가 동일 조인 구조를 사용합니다. 업무명 확인이 필요합니다.”라는 설명과 근거를 먼저 보여 준다. 그 아래 원본 SQL·AWR 구간·ASH 표본·통계 누락·계획·민감 컬럼·검증 사항을 펼친다.

권장 동작은 `기존 도구에 연결`, `API 초안 만들기`, `마트 후보로 검토`, `제외`다. 관측 SQL이 비효율적이거나 업무 의미를 알 수 없으면 그대로 API화하지 않는다. SQL·입력 스키마·OpenAPI/MCP·검증 질문을 초안으로 생성하되, 운영 게시 상태로 자동 전환하지 않는다.

### 운영자: 부하와 공급 상태를 본다

원천별 실행·대기·차단·취소 미확인, 마트 갱신의 마지막 성공/기준 시각, 요청 처리 단계, 권한 오류를 확인한다. 운영 중지는 질문·배치·수집에 적용할 범위를 표시하고 신규 실행을 즉시 차단한다. 진행 중 실행은 취소를 요청하고 DB 종료 확인 전까지 자원 점유를 유지한다. 장애에서 운영계 자동 우회는 없다.

## 6. 메뉴와 화면 원칙

| 메뉴 | 핵심 내용 | 기본 사용자 |
|---|---|---|
| 업무 질문 | 질문, 추천 질문, 조건, 결과, 근거와 요청 연결 | 현업 |
| 업무 도구 | 가능한 질문·지표·차원·기간·데이터 기준·담당자 | 현업·분석가 |
| 생성 요청 | 내 요청, 중복 연결, 담당자, 검토와 해결 상태 | 현업·운영자 |
| API 후보 | 업무별 묶음, 근거와 불확실성, 계약 초안, 검증 | DBA·데이터 담당 |
| 데이터 마트 | 대상 업무·범위·갱신·정합성·재사용·유지 비용 | 데이터 담당 |
| 운영 | 원천 부하 예산, APIC 연결, 감사, 배포 버전 | 운영자 |

현업 화면에서 SQL_ID나 캐시 적중률을 전면에 내세우지 않는다. 결과를 이해하는 데 필요한 지표 정의·기간·대상·기준 시각은 항상 보인다. DBA 화면에는 SQL과 판단 근거를 충분히 제공한다.

기본은 밝은 배경·짙은 본문·청록색 주요 동작. 실패/보류/완료를 색상과 텍스트로 함께 전달한다. Pretendard 우선, -3% 자간, 최소 12px 짝수 크기, 여러 줄 150% 행간을 적용한다. 키보드 동작·표의 스크린리더 설명·초점 복귀·오류 위치 표시를 구현 인수 조건으로 삼는다.

## 7. 없는 기능을 처리하는 제품 규칙

| 실제 이유 | 사용자 안내 | 시스템 처리 |
|---|---|---|
| 기간·점포 등 조건 부족 | 필요한 조건만 질문 | 도구 요청을 만들지 않음 |
| 권한 부족 | 허용 범위와 권한 절차 안내 | 접근 제한 데이터/도구의 존재를 불필요하게 노출하지 않음 |
| 부하·범위 제한 | 축소 범위·다음 갱신·비동기 검토 안내 | 무거운 요청을 신규 API로 우회시키지 않음 |
| 검색·설명 문제 | 기존 도구 연결 | 설명/동의어 개선 요청 |
| 데이터가 낡거나 없음 | 기준 시각·확보 범위 안내 | 적재·갱신 요청으로 분리 |
| 실제 기능 부족 | 생성·확장 요청 초안 | 기존 요청 중복 확인 후 등록 |

기본은 초안을 즉시 제안하고 사용자의 한 번의 클릭으로 접수한다. 조직이 자동접수를 선택할 수 있으나 원문 최소화·중복 병합·취소·감사 정책을 함께 둔다. 이는 제품 설계상의 승인 흐름이며 이번 설계 작업을 계속하기 위한 사용자 확인 요구가 아니다.

상태: `초안 → 접수 → 검토 → 정의 확인 → 개발 → 검증 → 게시 → 해결 확인`. 별도로 `보류·반려·중복 연결·취소`를 둔다. “게시”와 “질문 해결”을 분리하고, 사용자 확인 또는 승인된 검증 질문의 성공으로 해결 처리한다.

## 8. 잦은 조회의 사전 구성

처음부터 일·월·년 마트를 각각 만들기보다 **영업일×점포**의 최소 유효 단위를 정하고 합산 가능한 실적을 재사용한다. 상품군·고객·채널은 실제 요청과 권한을 확인한 뒤 추가한다. 월·연 단위가 충분히 빨라지지 않으면 상위 집계를 별도로 검토한다.

사전 구성 팩은 매출·재고·채권 등 **업무 템플릿**으로 제공한다. 고객마다 다른 테이블/업무 기준을 자동으로 확정했다고 주장하지 않는다. 설치 시 매핑→검증→소유자 확인→스케줄 활성화를 거친다. 재고 잔액은 기간 합산하지 않고, 객단가·비율은 분자/분모로 계산한다. 고유 고객 수는 일별 값 합산을 허용하지 않는다.

마트 승격 기준은 질문 횟수뿐 아니라 재사용 가능성, 전체 원천 읽기 비용, 허용 지연, 갱신·정정 비용, 저장 비용이다. 같은 측정 기간에 `절감 예상 = 기존 반복 조회 총비용 - (최초 적재 배분 비용 + 수집·증분·검증·재처리 + 저장·결과 제공 비용)`으로 가설을 세우고 파일럿에서 측정한다. 원천 부하 절감과 전체 운영비 절감은 따로 평가한다. 만료·미사용 마트의 폐기와 영향 도구 목록도 관리한다.

## 9. 성공 지표와 단계

| 검증 대상 | 측정 방법 | 완료 기준 제안 |
|---|---|---|
| 숫자의 신뢰 | 같은 지표·범위·시점의 기존 결과와 비교 | 금액 Decimal 기준 일치, 허용 오차를 지표별 명시 |
| 질문 해결 | 지원 범위 질문 중 정답/거절/요청 분류 | 승인된 검증 질문 전부 기대 경로로 처리 |
| 원천 보호 | 호출·DB time·logical/physical reads·CPU·대기, 배치 비용 포함 | DBA가 정한 총예산 이내, 임계 초과 신규실행 차단 |
| 도구 공급 | 접수→검증→게시→원질문 해결 시간 | 미충족 질문 1건을 끝까지 해결 |
| 요청의 안전 | 사용자/원천 누적 예산·권한·취소 검사 | 분할 호출·캐시 권한 우회 거절, 취소 미확인 격리 |
| MSTR 대체 | 특정 보고서군의 수치·필터·권한·내보내기 비교 | 선택한 보고서군 인수 승인; 전사 대체 주장 금지 |

POC: 한 팀·매출 한 업무·승인 도구 3개 안팎·마트 1개·후보 발굴·질문/표/차트·생성 요청 전체 흐름. MVP: 사내 인증, 감사, 버전·회귀, 배치 복구, 운영 보호, 설치 패키지. 이후 CDC/OLAP·보고서 예약·추가 업무를 늘린다. 상세는 06 문서.

## 10. 구현 전에 결정할 항목

우선순위 1: 실제 POC 업무와 기존 결과, APIC 실행·취소·신원 전달, 점포 권한의 정본, 순매출·취소·마감 규칙, 원천별 DBA 부하 한도, AWR/ASH 사용권과 반입 가능 형식.

우선순위 2: 요구 신선도, 집계 데이터 보존·과거 정정 기간, 설치 OS/CPU와 HA, 사내 LLM/AX 포털 연결, 보고서 출력 품질. PostgreSQL/OLAP 엔진 선택은 실제 스캔·동시성·갱신 요구로 결정한다.

사용자에게 이미 정해진 Rust/React·서버 설치·APIC 선호를 다시 묻지 않는다. 현재 문서와 시안 검토를 위해 운영 DB나 인증정보를 제공할 필요는 없다.
