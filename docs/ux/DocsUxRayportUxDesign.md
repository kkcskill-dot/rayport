# 레이포트 UI/UX 설계 v0.1

작성: 2026-11-08. 이 문서는 설계 제안이며 화면의 업무 데이터·사용량·시각·정책 수치는 모두 가상이다. 실제 운영 성능이나 연결 완료를 뜻하지 않는다.

## 1. 첫 화면에서 해결할 일

사용자의 시작점은 보고서 트리와 데이터베이스 목록보다 **업무 질문**으로 둔다. 승인된 API를 찾으면 결과와 함께 업무 정의, 기준 시점, 담당자, 접근 범위를 보여준다. 질문을 처리할 API가 없으면 질문 원문을 유지한 생성 요청으로 연결한다.

주요 화면 순서:

1. **업무 질문** — 질문 입력, 추천 예시, 결과 표, 답변 근거, 데이터 기준 시점, 후속 질문.
2. **업무 API** — 업무 용어 기반 검색, 입력 항목, 의미·최신성·권한 계약, 책임자, 버전.
3. **생성 요청** — 내 요청과 중복 요청, 정의·검증·승인·게시 진행 상태, 보완 질문.
4. **API 발굴** — BeLoga 파일로 반입한 ASH/AWR의 관측 SQL 패턴에서 업무 API 후보 검토.
5. **수요 마트** — 반복 조회를 위한 사전 구성, 기존 DW/DM 재사용, 갱신 부하와 지연.
6. **부하와 정책** — APIC 실행 연계, 원천별 예산, 오류·정합성·지연, 차단과 중지.

시안의 “설계 비교”는 제품 제작 의사결정을 위한 보조 화면이며 실제 운영 메뉴에 반드시 포함할 기능은 아니다.

## 2. 사용자별 정보 밀도

| 사용자 | 먼저 보여줄 것 | 상세 보기 |
|---|---|---|
| 업무 사용자 | 답, 업무 정의, 데이터 시점, 내 접근 범위, 다음 행동 | 사용한 업무 API, 담당자, 요청 진행 상태 |
| 업무 오너 | 용어·집계 기준, 요청 목적, 결과 예시, 의미 변경 | 버전 차이, 사용 부서, 품질 검증 |
| DBA/운영자 | 부하 상태, 제공 경로, 관측 근거, 승인 대기 | SQL 정규화 결과, 실행계획, 수집 범위, APIC 호출·중단 증적 |
| 관리자 | 계정·역할, 조직, 연결·파일 반입, 감사 | 라이선스 확인, 비밀 참조, 배포·복구 |

운영 구조를 설명하는 APIC·BeLoga·ASH/AWR·SQL 용어는 업무 질문의 주된 흐름에 노출하지 않는다. 시안은 검토 편의를 위해 업무/운영 메뉴를 모두 보여주지만 실제 제품에서는 역할로 노출과 권한을 분리한다. 화면 숨김은 서버 권한 검사를 대체하지 않는다.

## 3. 질문에서 생성 요청까지

```text
질문 입력
  → 현재 사용자에게 허용된 API 검색
  → 의미·필수 파라미터·최신성 조건 확인
  ├ 적합한 API 있음 → 정책 검사 → 허용된 제공 경로 → 결과와 근거 표시
  ├ 의미가 불명확함 → 짧은 확인 질문 또는 업무 정의 선택
  ├ API는 있지만 권한 없음 → 정보 노출을 제한한 접근 요청
  ├ API는 있지만 일시 장애/데이터 지연 → 상태와 허용된 대안 표시
  └ 적합한 API 없음 → 요청 초안 → 사용자 제출 → 기존 요청 중복 확인 → 담당자 배정
```

“없는 기능”을 장애·권한 없음·의미 불명확과 구별해야 한다. 권한 없는 API의 이름·스키마를 질문자에게 노출해서는 안 된다. 초안을 만드는 행위와 요청 제출, API 게시를 서로 다른 상태로 관리한다.

요청 초안은 원문 질문, 업무 목적, 지표·차원, 조회 범위, 원하는 결과 형태, 허용 지연, 반복 사용 여부, 업무 담당 후보를 가진다. 자동 추론 필드는 “제안”으로 표시하며 담당자가 수정할 수 있어야 한다. 한 질문에 반복 제출해 중복 요청이 쌓이지 않도록 사용자 범위 idempotency와 중복 후보 연결을 둔다.

사용자가 요청 버튼을 누르면 레이포트 내부 요청함에 생성한다. 외부 티켓·메일·메신저 전송은 별도 연계 설정과 전송 권한을 갖춘 후 적용한다.

요청 상태: `초안 → 제출 → 정의 확인 → 검증 → 승인 대기 → 게시 → 원 질문 재실행`. 보류·반려는 이유와 필요한 보완 항목을 보여준다. 게시 완료 시 알림에서 원 질문을 다시 실행할 수 있게 한다.

## 4. API 발굴 화면

왼쪽은 후보 목록, 중앙은 업무 설명과 후보 계약, 오른쪽은 근거·검증·정책 패널로 구성한다. 기본 목록은 단순 SQL 실행 횟수 순위 대신 업무 수요와 재사용 가능성, 관측 근거의 충실도, 현재 소스 부하, 기존 API와 중복 여부로 검토 우선순위를 제안한다.

후보 카드의 필수 정보:

- 업무 이름 초안, 관련 테이블과 지표, SQL 패턴 묶음, 관측 구간과 범위.
- ASH 활동 표본과 AWR의 포착된 SQL 실행 델타를 구별한 표시.
- BeLoga 원본 파일·반입 배치·원천 DB의 식별자와 증적 링크.
- SQL 원문·리터럴의 마스킹 상태, 수집 누락과 의미 추론의 불확실성.
- 입력·출력 계약, 예상 사용 부서, 소유자, 제한된 시험 경로.
- 기존 API/DW/DM 활용 가능성, 복제본/캐시/수요 마트 등 제공 경로 제안.
- “계약 초안 생성”, “업무 검토 요청”, “DBA 검증”, “게시”를 구분한 행동.

ASH/AWR 분석은 자동으로 후보와 검토 자료를 만들 수 있지만 업무 의미·권한·실행 영향을 확인하지 않은 API를 운영에 자동 게시하지 않는다. 라이선스·수집 권한 확인은 설치 관리 흐름에서 처리하고 일상 업무 화면에는 관련 기술 설명을 반복하지 않는다.

## 5. 수요 마트 화면

기존 DM을 연결할 수 있으면 우선 활용한다. API 수요가 반복되고 현재 경로의 비용이 높으며 허용 지연이 있는 경우에만 새 사전 구성을 제안한다. “인기 질문”과 “새 물리 마트 필요”는 같은 상태가 아니다.

마트 카드: 업무 정의, 데이터 입도, 연결 API, 허용 지연, 현재 워터마크, 정합성 상태, 갱신 방식·주기, 마지막 성공과 실패, 원천 추출 예산, 담당자, 보관 기간.

승격 판단은 반복 조회 절감 비용과 갱신·보관·운영 비용을 함께 본다. 실제 측정치가 없으면 절감률이나 ROI를 수치로 단정하지 않고 “측정 전”으로 표시한다. 초기 적재·정정·삭제·재처리와 정합성 확인도 운영 부하에 포함한다.

마트 장애 시 사용자는 “최신성 조건 안에서 이전 결과 제공”, “갱신 대기”, “요청 중지”를 구분해 본다. 운영 원본으로 자동 우회하지 않는다.

## 6. MSTR 보고서군 전환

기존 사용자가 바로 자연어 질문에 적응해야 한다고 가정하지 않는다. 초기 홈에는 기존 업무 분류와 친숙한 보고서명으로 찾는 진입점도 제공한다. 하나의 보고서군을 API와 화면으로 옮길 때 필터·권한·집계·기간·통화·드릴다운·합계 일치 여부를 검증한다.

진행 상태는 `기존 보고서 연결 → 계약 정의 → 표본 대조 → 사용자 병행 사용 → 전환 승인`으로 둔다. 시안의 미수금 조회는 이러한 전환 대상의 가상 예시이며 실제 MSTR 보고서와 매핑되지는 않았다.

## 7. 시각 언어와 접근성

- 밝은 업무 화면, 짙은 남색 본문, 청록색 주 행동. 경고는 호박색, 상태는 색과 문구를 함께 표시.
- Pretendard 우선, 시스템 폰트 대체. 외부 폰트/CDN 요청 없이 동작.
- 자간 −3%, 짝수 글자 크기, 최소 12px. 여러 줄 텍스트는 최소 150% 줄 높이.
- 테이블의 금액·기준일·비교 기간을 명확히 하고 데이터 시점을 결과 가까이에 유지.
- 키보드 포커스, 명시적 입력 label, 현재 메뉴 상태, 상태 알림의 `role=status` 제공.
- 넓은 화면은 탐색/결과/신뢰 정보, 좁은 화면은 가로 탐색과 한 열. 데이터 표는 필요한 경우 가로 스크롤.
- 빈 화면·조회 중·결과 없음·의미 불명확·접근 제한·데이터 지연·실행 중단을 서로 다른 상태로 설계.

## 8. 현재 산출물과 검증 한계

- `apps/web`: React/TypeScript/Vite 시안 소스, 일곱 화면 전환, 질문 예시, 생성 요청의 메모리 상태, API 초안 상태, 혼잡 시뮬레이션.
- `docs/prototypes/DocsPrototypesRayportPreview.html`: 외부 요청·로컬 서버 없이 여는 단일 HTML/JavaScript 시안. 초기 질문 화면 아래 DW/DM과 레이포트의 역할 흐름 비교 포함.
- 두 시안의 “질문 분석”은 키워드로 데모 경로를 선택하는 동작이다. 실제 자연어 처리·API 매칭·SQL 실행·APIC·BeLoga 파서는 구현하지 않았다.
- 생성 요청은 브라우저 메모리에만 존재하고 새로고침하면 초기화된다. 영구 저장·인증·인가·행 단위 필터는 후속 구현이다.
- 2026-11-08 공식 npm registry에서 의존성 버전을 확인해 고정했다. Node/npm을 찾지 못해 설치·lockfile 생성·타입 검사·빌드는 수행하지 못했다. 새 도구 체인이나 서비스는 실행하지 않았다.
- 후속 완료 기준: 승인된 개발 환경에서 의존성 설치와 lockfile 생성, 타입 검사/빌드 통과, 360px·728px·데스크톱 화면과 키보드 흐름 확인, 실제 API와 오류 상태 연결.


## 9. 프론트 구조와 이번 확인 범위

전체 경로를 이어 붙인 유일 파일명 규칙을 적용했다. `domain`은 순수 타입, `application`은 질문/생성 요청의 프레임워크 독립 순수 상태 전이와 포트, `infrastructure/demo`는 가상 데이터와 데모 분류, `presentation`은 화면과 공통 컴포넌트, `bootstrap`은 React 시작 지점으로 분리했다. 일곱 화면은 각각 독립 파일이며 한 App 컴포넌트에 전부 넣지 않았다.

별도 서버 없이 macOS JavaScriptCore에서 정적 HTML의 스크립트 문법을 확인하고, DOM stub으로 초기 비교 흐름·미지원 질문·생성 요청·중복 방지·요청 목록·혼잡 상황·사용자 입력 HTML escaping 일곱 항목을 확인했다. 이는 브라우저 렌더링/접근성 검증이나 React 타입 검사·빌드를 대신하지 않는다. JSON 형식과 로컬 import 대상 파일 존재도 확인했다.

의존성은 `presentation → application → domain`, `infrastructure → domain`이며 bootstrap이 `RayportSessionData` 포트에 demo 어댑터를 주입한다. application과 presentation은 infrastructure를 직접 가져오지 않는다. React hook은 `presentation/bindings`에 두고 application의 순수 상태 전이 함수를 호출한다. application은 React를 import하지 않는다.
